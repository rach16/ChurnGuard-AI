# ChurnGuard AI

Customer-churn analysis for B2B SaaS: a dbt warehouse over synthetic customer
engagement data, a RAG pipeline over the supporting documents, and LangGraph
agents that turn both into retention recommendations. Demonstration project —
all customer data is generated by `scripts/generate_synthetic_rag_data.py`.

## Architecture notes

`docs/ARCHITECTURE.md` is the design of record — read it before proposing
structural work. In short: the product predicts a churn **date with a confidence
interval**; the warehouse is authoritative for every number, the vector store for
narrative only.

Things the directory tree does not tell you:

- **Scoring exists twice, deliberately.** `src/core/health_scoring.py` serves the
  API; `warehouse/models/gold/customer_health_score.sql` makes the same number
  queryable by SQL clients. `tests/test_warehouse_parity.py` recomputes all 200
  customers both ways and fails on divergence. Change one, change both.
- **Weights live in two places by design.** `RISK_WEIGHTS` in Python,
  `vars:` in `warehouse/dbt_project.yml`. They must match.
- **The dataset is deterministic.** Fixed seed and a fixed `AS_OF_DATE`, not
  `datetime.now()`. Rolling windows anchor to the data's own as-of date.
- **One backend, two modes.** `api.py` is the only entrypoint. Without
  `OPENAI_API_KEY` or Qdrant it serves CSV-backed endpoints and returns 503 with
  a specific reason on LLM ones. `/health` is liveness, `/ready` is readiness.
- **Qdrant runs in Docker** (`churn-qdrant`). `QDRANT_URL` also accepts
  `:memory:` or `local:<path>` so tests and CI need no container.

## Commands

```bash
uv run python src/backend/api.py                    # API
uv run --extra dev --extra warehouse pytest tests/  # tests
python3 scripts/validate_dataset.py                 # 28 data contracts
uv run python scripts/benchmark_retrieval.py        # retrieval, no API cost
uv run --extra warehouse python scripts/report_exposure.py   # cost of inaction
cd warehouse && DBT_PROFILES_DIR=$PWD uv run --project .. dbt build
AWS_PROFILE=personal uv run --extra warehouse python warehouse/verify_athena.py
```

Use `uv run`, not bare `python3` — most scripts need the project venv.
`load_dotenv(".env")` explicitly; `find_dotenv()` fails when run from stdin.

## Standing instructions

- **Do not drift.** Work the phase item that was agreed. Do not reorder phases,
  add stages, or start adjacent work because it seems valuable.
- **Flag, don't add.** Out-of-scope improvements get raised as a proposal with
  cost and effort, and are recorded under Deferred in STATUS.md if declined.
  They do not get built unprompted.
- **Use the existing phase numbering.** New work is a sub-item of an existing
  phase (4.4, 2.5) unless a new phase is explicitly agreed. Phase numbers are
  **identifiers, not an order** — commit messages and ADRs reference them, so
  they never change. Execution order lives in the Step column of STATUS.md and
  is expected to change; do not renumber a phase to make it sort correctly.
- **No unevidenced numbers.** Every metric in docs or code comments names the
  script that produced it and the date. If it has not been measured, say so.
  ADR-0007 records why this rule exists.
- **Never commit or push unless asked.** Branch, commit at phase boundaries,
  merge to main only on request.

## Maintenance rule

Update `.claude/STATUS.md` whenever any of these happens:

| Trigger | Action |
|---|---|
| A phase item completes | Move it from Next to Completed with its commit hash and what measurably changed |
| A metric is re-measured | Record the new value **with the date measured**. Strike through the old one — `~~0.150 (2026-08-30)~~ → 0.941 (2026-08-31)`. Do not delete it. |
| A scope decision is made | Add to Deferred or Rejected **with the reason**. Do not delete these sections. |
| A gap is found or closed | Update Known gaps |
| A phase item completes | Also set its **FDE roadmap** cell, and update the roadmap coverage table if the area's status changed |

The README carries measured numbers too. When a metric changes, check whether
README.md repeats it — STATUS.md being current is not sufficient.

Never anchor an edit to STATUS.md on a commit hash. Resolve the hash from
`git log --grep` at write time; a hardcoded one silently matches nothing and the
row is dropped without an error.

Superseded facts stay visible, struck through. The history of what a number used
to be is the point — a figure that silently changes cannot be audited.
